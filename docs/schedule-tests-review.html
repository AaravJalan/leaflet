Schedule tests review

StrongOne medium gap, a few small ones

This is a careful suite. It checks behavior users rely on, uses fixed dates, and goes after the date bugs that usually slip through: Sunday placement, month and year rollovers, leap days and daylight saving. Its main gap is that it never says what should happen when an event's end is before its start.

  • 77 / 77 passing
  • Passed in UTC, Chicago, Auckland, Santiago
  • Every exported function tested

What it does well

  • No dependence on today's date. Every test uses fixed dates in 2026 or 2024, and nothing calls Date.now(), so the suite won't break as time passes.
  • Expected values come from a separate path. The at() helper builds dates with new Date(y, m, d, h, min), while the code parses strings and uses setDate. A shared bug would have to exist in both.
  • A sweep over four years. mondayOf is checked on 1,464 consecutive days, which covers every daylight saving change in that range in whatever time zone CI uses.
  • Round trips. Values are saved with buildWhen and read back through the edit-form helpers and formatWhen, which is the path the app takes.
  • Messy real-world input. Leftover fields from the other schedule mode, old records with no repeatDays, and unknown day numbers are all covered.
  • Readable. it.each tables and test names like “Sunday belongs to the week that started six days earlier” work as a spec for the code.
  • CI backs up the time zone claim. The workflow runs the suite in three time zones. I also ran it in America/Santiago, where clocks change at midnight, and it passed.

Gaps, most important first

I confirmed each of these by running the code in a temporary test, which I deleted afterward.

Medium

End before start is never tested

Nothing checks that the end comes after the start. A one-time event from 8:00 PM to 6:00 PM is saved as typed. A weekly event from 10:00 PM to 1:00 AM is saved with the end on the same day as the start, three hours earlier, but it still displays as “10:00 PM to 1:00 AM”. The forms accept both because the inputs are separate fields. Anything that later sorts by end time or checks whether an event is over will get these wrong.

Suggested test 
it('rolls an overnight weekly end into the next day', () => {
  const r = buildWhen('weekly', '', '', WEEK, '22:00', '01:00', [MON])
  expect(r.endsAt).toBe(at(2026, 11, 10, 1, 0))
})

it('rejects a one-time end before its start', () => {
  expect(() => buildWhen('once', '2026-11-09T20:00', '2026-11-09T18:00', '', '', '', []))
    .toThrow()
})

Both tests fail today. Decide what the right behavior is, then change the code to match.

Low

Daylight saving checks for dateInWeek only cover US dates

The two daylight saving tests use the US change dates. In the UTC and Auckland CI runs, nothing changes on those dates, so the tests pass without testing anything. The four-year sweep only covers mondayOf. Running a similar loop over dateInWeek (every week, every weekday, checking the date and wall-clock time) would make each time zone in CI check its own daylight saving changes.

Low

The “order given” test can't detect a shared array

buildWhen returns the caller's days array as repeatDays, so both names point to the same array. The test checks that days wasn't changed, but buildWhen never changes it, so that check can't fail. If the form changes its own days array after saving, the saved object changes with it. Add expect(result.repeatDays).not.toBe(days) and copy the array in buildWhen, or drop the check that tests nothing.

Low

Invalid input has no defined behavior

A malformed week saves NaN for both weekOf and startsAt without any error. A time of 25:00 moves the event to 1:00 AM the next day. An unknown day number such as 9 moves the start into the following week. The native date and time inputs make these unlikely from the UI, which is why they're low priority. One test that rejects a bad week would still stop NaN from reaching Firestore.

Style

Some checks depend on another function under test

The ymd() helper calls toDateInput, which is also being tested. If toDateInput broke, the mondayOf and dateInWeek tests would fail too and point you to the wrong place. It's a small cost, since toDateInput has its own tests. Comparing getFullYear(), getMonth() and getDate() directly would remove the link.
